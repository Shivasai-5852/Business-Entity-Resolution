1. OBJECTIVE & ARCHITECTURAL DESIGN
--------------------------------------------------------------------------------
The objective of Stage 3 is to construct a production-grade, memory-efficient,
and idempotent text preprocessing module tailored to business entity matching
across heterogeneous data sources in the United States, India, and France.

Key Architectural Principles:
1. Dual-Representation Strategy:
   - Conservative Representation ('conservative'):
     Preserves exact tokens, legal designators, and accents while cleaning
     formatting anomalies. Used during stage 4/5 verification to avoid false
     positives and protect precision (vital for the F0.5 metric).
   - Normalized Representation ('normalized'):
     Aggressively standardized (Latin accents stripped, punctuation normalized,
     trailing corporate suffixes removed, street abbreviations unified). Used
     for candidate generation and high-recall inverted index lookup.
2. Complete Script Preservation:
   - Strict preservation of non-Latin scripts (Devanagari Hindi, U+0900 to U+097F).
   - Combining marks (matras, vowel signs, nuktas, chandrabindu) are never
     corrupted, transliterated, or deleted.
3. Safe Missing Address Invariance:
   - Empty or whitespace-only addresses remain strictly empty ("") and are flagged
     with 'is_empty: True'. They NEVER map to placeholder tokens like 'UNKNOWN'
     or 'N/A', preventing catastrophic false-positive clustering in Stage 4.
4. Entity ID Independence:
   - Entity IDs are strictly isolated as record identifiers and never ingested
     as matching features.

2. DETAILED NORMALIZATION RULES
--------------------------------------------------------------------------------

A. Unicode NFKC Normalization (normalize_unicode_nfkc):
   - Decomposes compatibility characters and recomposes them to canonical forms.
   - Normalizes ligatures (e.g., 'ﬁ' -> 'fi', 'ﬂ' -> 'fl'), fullwidth characters
     (e.g., 'ＡＢＣ' -> 'ABC'), and compatibility superscripts/subscripts.
   - Retains Devanagari and Latin characters in canonical Unicode.

B. Case Normalization (to_lower):
   - Converts text to lowercase across all cased alphabets (Latin, Greek, Cyrillic).
   - Leaves un-cased scripts like Devanagari completely unaltered.

C. Whitespace Normalization (normalize_whitespace):
   - Collapses arbitrary consecutive whitespace (spaces, tabs, newlines,
     carriage returns, non-breaking spaces U+00A0) into a single ASCII space.
   - Strips leading and trailing whitespace boundaries.

D. Safe Punctuation & Combining Mark Preservation (normalize_punctuation):
   - Precomputed C-level translate table mapping Unicode punctuation ('P') and
     symbol ('S') categories to ASCII space.
   - Ampersands ('&') are explicitly converted to ' and '.
   - CRITICAL IMPLEMENTATION DETAIL:
     Standard naive regexes like `re.sub(r'[^\w\s]', ' ', text)` strip Devanagari
     combining vowel marks ('Mc') like 'ा' (0x093e in 'राम'), destroying Hindi
     words into isolated consonants ('र म').
     Our custom category translator strictly preserves all Letters ('L'),
     Numbers ('N'), and Combining Marks ('M': 'Mc', 'Mn', 'Me'), ensuring 100%
     intact preservation of Hindi words, matras, and conjuncts.

E. Selective Latin Accent Stripping (strip_accents):
   - Generates an accent-insensitive view for Latin text (e.g., French 'École' ->
     'Ecole', 'Sàrl' -> 'sarl', 'Hôtel' -> 'hotel', 'Noël' -> 'noel').
   - Decomposes characters via NFD and removes ONLY combining diacritical marks
     in the Latin diacritic block (U+0300 to U+036F, U+1DC0 to U+1DFF, U+FE20 to
     U+FE2F).
   - Devanagari nuktas (e.g. 'ग़', 'ज़') and chandrabindus ('ँ' in 'आँख') belong
     to the Devanagari Unicode block and are strictly preserved.

F. Corporate Legal Suffix Extraction (extract_corporate_suffix):
   - Multi-jurisdiction coverage across US, India, and France:
     * US: inc, corp, llc, llp, lp, co, ltd, company, incorporated, corporation,
       limited liability company, professional corporation, etc.
     * India: private limited, pvt ltd, pvt limited, private ltd, limited, ltd,
       llp, co-op; Devanagari: 'प्राइवेट लिमिटेड', 'प्रा लि', 'लिमिटेड', 'लि',
       'कंपनी', 'कॉर्पोरेशन'.
     * France: sarl, sas, sasu, sa, sci, eurl, snc, gie, sca, scs, ste,
       societe a responsabilite limitee, societe par actions simplifiee, etc.
   - Loop-based compound suffix stripping:
     E.g., 'Acme Co Ltd' -> strips 'ltd' then 'co' -> core name 'Acme', suffix 'ltd'.
     E.g., 'International South Consultants Private Ltd' -> strips 'ltd' then
     'private' -> core name 'International South Consultants', suffix 'pvt ltd'.
   - Fast O(1) early exit:
     Checks `lower_accent_stripped[-1] in _LAST_SUFFIX_WORDS` before scanning suffix
     patterns, skipping the iteration for the majority of non-suffix tokens.
   - Stopword Safety Fallback:
     If stripping leaves an empty string or only generic stopwords (e.g. 'The Company',
     'Inc.', 'Le Groupe', 'A Corporation'), stripping is aborted and the original
     name is preserved to prevent non-distinct matching keys.

G. Business Address Standardization (normalize_business_address):
   - Normalizes common street, route, and unit abbreviations:
     * US/EN: street -> st, avenue -> ave, boulevard -> blvd, road -> rd,
       drive -> dr, lane -> ln, court -> ct, suite -> ste, apartment -> apt, etc.
     * India: taluk/taluka -> tq, district -> dist, opposite -> opp, near -> nr,
       sector -> sec, phase -> ph, nagar -> nagar, colony -> colony.
     * France: rue -> r, boulevard -> bd, allee -> all, impasse -> imp, route -> rte.
   - Missing Address Invariance:
     Empty or whitespace-only inputs strictly return `is_empty: True` and `normalized: ""`.
     Missing addresses are never coerced into shared tokens.

4. KNOWN LIMITATIONS & EDGE CASES
--------------------------------------------------------------------------------
1. Embedded Corporate Suffixes:
   - Suffix stripping is intentionally anchored to trailing tokens. Names where
     a corporate word is embedded medially (e.g. 'Holloway Peak Inc Seafood' or
     'The Corporation for Public Broadcasting') are deliberately preserved to
     avoid corrupting distinctive brand identifiers.
2. Cross-Script Transliteration:
   - Preprocessing intentionally does NOT transliterate Devanagari Hindi into Latin
     (e.g., 'राम' is not transliterated to 'Ram'). Transliteration is lossy,
     ambiguous, and violates competition constraints. Cross-script matching
     in Stage 4/5 should use subword/character n-grams or bilingual embeddings.
3. Unseen Regional Abbreviations:
   - While major French ('r', 'bd', 'av') and Indian ('tq', 'dist', 'sec') terms
     are mapped, highly localized municipal abbreviations may remain unexpanded.
     This is addressed by using character n-gram token similarity in downstream
     matching rather than strict exact token equality.

5. INTEGRATION PLAN FOR STAGE 4 (CANDIDATE BLOCKING & GENERATION)
--------------------------------------------------------------------------------
The outputs of this preprocessing module directly feed into the candidate
generation pipeline in Stage 4:

1. Blocking Keys Construction:
   - Partition 1: Exact Country Code ('US', 'India', 'France') -> 100% precision
     filter with zero cross-border leakage.
   - Partition 2: Inverted Index on distinctive tokens from `name_normalized`
     (excluding high-frequency stopwords and corporate terms).
   - Partition 3: Character 3-gram MinHash / prefix blocking on `name_normalized`
     for typo tolerance.

2. Conservative Feature Verification:
   - In Stage 5 (Pairwise Matching & Classification), both `name_conservative`
     and `name_corporate_suffix` will be compared alongside `name_normalized`.
   - Matching pairs must pass high-precision verification on full conservative
     tokens to satisfy the stringent F0.5 evaluation metric.
